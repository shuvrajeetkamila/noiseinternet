EXE checked in with no reproducible build behind it is the sort of thing this project exists to avoid.

The numbers above are the build of commit `e9aae06`, the first one whose Windows exe is the windowed app,
and they are an **example, not the current truth**: every green push republishes these files under the same
tag and the build is not byte-reproducible. The debug
keystore is created fresh on each runner, so the APK's signature bytes move even when only a `.md` file
changed, and the same C++ compiled twice by MSVC came out at an identical size with a different sha256. The
manifest in the release body is generated on the runner from the bytes it publishes, so that - not this
table - is what to verify a download against (`sha256sum` your copy, compare with the release page).

The packaging step is not asked to believe the CMake option: it runs `dumpbin /dependents` on the exe that
was actually linked and records the verdict. From the current run's `BUILD-INFO.txt`:

```
crt:  STATIC (/MT): the exe imports no CRT DLL, so it is standalone; redist/ is a fallback only
pkg:  NoiseInternet.exe imports: KERNEL32.dll ole32.dll WS2_32.dll
file: PE32+ executable (console) x86-64, for MS Windows, 7 sections
```

The first attempt at this published a `/MD` exe anyway, because under CMake policy `CMP0091=NEW` the
runtime is chosen by `CMAKE_MSVC_RUNTIME_LIBRARY` rather than by a `/MD` sitting in the flag variables, so
the string replace had nothing to replace (defect 28 in `reports/RESULTS.md`). The import-table check is
what caught it, one build after it happened, instead of a README asserting a property nobody measured.

Both come from `.github/workflows/build.yml`, and the release job only runs when the Android and
Windows jobs are green: the APK step fails if the native library is missing from the archive, the EXE
step fails if no PE was produced, and the manifest above is generated by `stat`/`sha256sum` on the
runner, not typed by hand. The `file` output quoted for the EXE is also the runner's, not a
description of intentions.

## What these artifacts do NOT mean

* **Neither binary has ever played or recorded audio.** The build hosts have no sound hardware
  (`ni audit`: 0 audio devices), and neither has been run on a phone or a PC with a loudspeaker and a
  microphone. Gate F stays NOT TESTED.
* **No message has crossed real air.** The link is measured through the modelled device chain only,
  where a 2 kB session completes and is hash-verified (`reports/linksim.csv`, `reports/RESULTS.md`
  §4.6). A 4 MB APK is not evidence about acoustic performance.
* The proxy and VPN-tunnel legs are unverified: `ni demo` does not pair (defect 21) and the Android
  tunnel service has never been started on a device. Gate E stays FAIL.
* On Windows the core compiles and **8 of 8 unit-test suites pass**, the same as on Linux. The number is
  recent history worth knowing: the first Windows runs were 7/8 with `t_arq` red, and that one suite was
  reporting a real use-after-free in the ARQ out-of-order replay path that Linux's allocator masked
  (defects 24-25 in `reports/RESULTS.md`). The run that published these files is the run that went green
  after the fix - so the Windows artifact is "compiles, and the unit suites pass", which is still not
  "tested on a sound card".
  * `lint`, `assembleRelease`, and any device install were never exercised on the Android side beyond
  `assembleDebug`.
* **These binaries are not reproducible builds.** Nothing in this repository claims otherwise: the debug
  signing key is per-run and no source-date normalisation is set up, so a hash pins a *download*, not
  a build. Verifying a binary means checking it against the manifest published with it, or rebuilding from
  the commands below and accepting that the output will differ byte-for-byte from the asset while the
  compiled code paths are the same.

## Building them yourself

* Android: `android/build_apk.sh`, or open `android/` in Android Studio. It needs JDK 17 and the SDK
  packages named in `android/BUILD.md`; the script checks for each and says which one is missing
  instead of pretending.
* Windows: `cmake -S windows -B build` then `cmake --build build --config Release` (see
  `windows/BUILD.md`). CTest runs from the build directory; its result is reported by CI.
* On Linux the same engine builds with `scripts/build_local.sh`, and that is where every number in
  `reports/` was produced.
