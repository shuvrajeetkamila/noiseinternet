# NOISE INTERNET — measured results

Everything below was produced on the build host (Linux, no audio hardware, 2 cores) inside the
Arena sandbox on 2026-10-13. Numbers are copied from command output, not estimated. Anything that
could not be measured here is listed in section 7 as NOT TESTED rather than described as working.

Reproduce with:

```sh
PATH=/home/user/env/bin:$PATH bash scripts/build_local.sh          # library + CLI + 8 test binaries
cd build-linux && ctest --output-on-failure                         # the automated suite
./ni audit && ./ni profiles && ./ni selftest --profile all --trials 8 --snr 25
./ni calibrate --trials 3 --snr 25
./ni bench --profile 2,3,5,10,11 --trials 3 --csv reports/bench_sweep.csv --json reports/bench_sweep.json
./ni linksim --bytes 228 --trials 2 --max-ms 3000 --profile 3 --snr 35 --no-multipath --json
python3 scripts/raw_to_csv.py      # writes reports/*.csv from reports/raw/
```

### Defects found while building this (47 items: 41 fixed; 17, 20, 22, 23, 27, 41 documented, not fixed)

Items 1-8 and 10-14 were caught by the tests above. Items 9, 15 and 16 came from reading the
simulator's per-side diagnostics after a run failed to deliver anything, which is why they are listed
here as well: a green suite did not find them, and neither did a single end-to-end run.

1. **Wrong SHA-256 round constant.** `kK[38]` was `0x81c1979b`, which is not a SHA-256 constant at
   all (the FIPS value is `0x81c2c92e`). Every digest was wrong, so HMAC, HKDF, the SAS code and the
   session keys were non-standard — while every round-trip test kept passing, because both ends used
   the same broken hash. Caught only by checking against published RFC vectors. `t_crypto` now
   includes the four FIPS examples.
2. **Wrong generator polynomial.** `error_correction.cpp` used `kG1 = 0x6B` (octal 153) while the
   headers documented 133/171. Free distance of (153,171) is **8**, of (133,171) is **10** — the
   documented code is the better one and the code did not match its own documentation. Found by
   computing `d_free` in two independent ways (BFS in the test, a DP plus a brute-force search in
   `python/gen_vectors.py`). Measured effect on the same channel: 1 136-bit block at 3.333 % raw BER
   went from 8.876 % residual bit errors to 0.0734 %, and at 16 bits/symbol from 111 wrong
   information bits to 0.
3. **BER reported without FEC was fiction.** In the no-FEC path `info_bits` was filled from
   `soft_coded[i] >= 4`, i.e. every "unknown" metric counted as a 1, so the reported post-FEC error
   rate (0.236) did not match the actual raw rate (0.092). Now `info_bits[i] = hard_coded[i]` and the
   two agree (0.2098 on all six attempts of the verification run).
4. **Replay window rejected valid out-of-order frames.** When the window advanced, the slots it
   vacated kept their old marks, so a frame that arrived late inside the window was refused as a
   replay — precisely the frames selective retransmit exists to deliver. The vacated slots are now
   cleared.
5. **Burst packer treated "burst is full" as an error.** `pack_frames()` returned the encoder's
   `NI_ERR_SHORT` when the next frame did not fit; the caller reads a negative as "nothing to send",
   so **any message that needed more than one burst was never transmitted at all**, on any profile.
   A 2 500-byte transfer made no progress for seconds at a time. Now the burst simply ends there
   (12 fragments in 3 bursts, all delivered, `lost_frames = 0`).
6. **Unacknowledgeable frames leaked.** A frame queued with `want_ack = false` can never appear in
   the peer's cumulative acknowledgement, so it stayed in the transmit queue forever: `pending` lied
   and the queue grew for the life of the session. Best-effort frames are now released once on the
   wire.
7. **Pairing frame sequence space was inconsistent.** Pairing frames consumed reliable sequence
   numbers, but the receiver only advanced its cumulative ack on DATA delivery, so a handshake frame
   could never be acknowledged and (an in-flight item is never re-sent) the handshake stalled with one
   copy of each frame on the wire.
8. **Initiator never installed its session keys.** `Node::start()`'s `on_pair` callback checked for
   `DONE` *before* calling `next_frame()`, which is where the initiator reaches `DONE`. So A stayed
   keyless while B demanded an authenticated MAC on every control frame: each side silently discarded
   the other's frames forever. The check now runs on both sides of the call.
9. **`Node::start()` / `AcousticLink::start()` were not idempotent.** A second call rebuilt the modem
   without freeing the first (a leak that never frees) and re-issued `begin_pairing()`, which threw
   away the nonces the peer was working from. The link simulator started each node twice, and every
   pairing then failed its HMAC. Both start paths are now one-shot.
10. **Responder could not restart after a failed attempt.** After `FAILED`, `next_frame()` always
    returned the initiator's state (`WAIT_RESPONSE`) regardless of role, so a responder whose
    passphrase was mistyped once turned into an initiator and the handshake could never be retried
    from either side. It now returns to the state its own role starts in, and the responder's
    *confirmation* check feeds the same attempt counter and backoff as the initiator's (without it,
    an attacker could try confirmations at the responder without limit).
11. **`confirm_sent_` latch was never cleared**, so a responder that had answered once could never
    answer again, no matter how often the user retried.
12. **Out-of-bounds read in the SAS alphabet.** `static const char* words[64]` held **62**
    initialisers, so indexes 62 and 63 were null pointers; any pairing whose code drew one of those
    indexes died inside `strlen(NULL)` (found by AddressSanitizer, ~12 % of handshakes). The array is
    now unsized with a `static_assert` on 64 entries.
13. **Plaintext DATA accepted during the pairing race.** The receiver refused unencrypted DATA only
    when it already had keys, so the side that had not installed keys yet accepted whatever an
    on-path attacker sent. `require_crypto` now means "refuse unencrypted DATA", keys or not.
14. **Unbounded failure penalty in the channel estimator.** Each CRC failure subtracted 6 dB from the
    reported band SNR with no floor; a receiver that could not read its peer racked up hundreds per
    second and reported −4 659 dB, which then poisoned the squelch and adaptation. Floored at −45 dB.
15. **Turn-taking ignored the render queue.** The link counted a burst as sent when it was copied out
    of its own buffer, not when it was played, so an endpoint drained faster than real time spoke over
    the peer's reply window and every timing figure measured host speed rather than sound travel.
    `Node::step()` now reports the outstanding samples (`set_tx_backlog`) and the ARQ clock keys off
    playback; `--unpaced` keeps the old fast-but-unrealistic mode for comparison.
16. **Calibration ranked profiles with a zero throughput term.** `PhyTestResult::payload_bps` was
    declared, printed by `ni calibrate` and consumed by `ChannelEstimator::suggest()` (`eff =
    payload_bps * coding-penalty`), but `ni_phy_test()` never assigned it — so the column printed `0`,
    every band's effective rate was 0, and the recommendation was driven by frame success alone.
    `reports/raw/calibrate.txt` now shows the measured rates (DBPSK-MID 1 219 b/s, DBPSK-WIDE 2 400,
    QAM16-WIDE 6 400 on the modelled chain); the "0 usable" line in that file is the reliability term
    talking, not this bug.
17. **`--snr` is not the signal-to-noise ratio you get** (found by `ni bench`, **not fixed**). The
    channel model adds noise after AGC has normalised the signal, so the achieved SNR lands in a band of
    about 4-26 dB regardless of the requested value: `--snr 30` measured 20.2 dB, `--snr 0` measured
    12.1 dB (medians in `reports/bench_sweep.csv`). It is left unfixed deliberately: every published
    number in this file was taken through that model, and silently changing the noise reference would
    invalidate them all without any hardware to re-baseline on. Until it is fixed, quote the measured
    column and never the nominal one, and do not describe a `--snr 35` run as a clean-channel run.
    *Status after defect 19:* the model now adds noise in front of the AGC, scaled from a one-second
    long-term level, and the whole sweep was re-run (`reports/bench_sweep.csv`). Requested SNR is now
    tracked more closely at the low end but still saturates near 26 dB (30 -> 25.7, 22 -> 25.0,
    16 -> 23.4, 8 -> 19.6, 0 -> 15.1 dB measured) because of the receiver distortion floor described in
    item 20, so the rule stands: quote the measured column, never the nominal one.
18. **Bursts larger than the PHY could carry were dropped without a word** (root cause of `delivered 0`;
    see section 4.6, **fixed**). `ArqConfig::max_burst_bytes` (1024) was never bounded by the modem's
    per-burst PDU capacity (82 bytes on FD-LOW-DBPSK), `Modem::tx_render` correctly refused the oversized
    burst, and `AcousticLink::render_burst` swallowed the error while the ARQ marked those frames in
    flight. Paired with four other defects in the same path; all are described in section 4.6.
19. **The channel model was not a channel, it was 10 separate channels** (**fixed**). Every
    `AcousticChannel::process()` call re-zeroed the loudspeaker and microphone biquads, restarted the
    air-absorption pole and the AGC loop from scratch, computed the noise level from the RMS of the block
    being processed, and re-seeded its noise generator with the *same seed*, so the "background noise" was
    one identical pattern repeated in every block. A burst that straddled two audio callbacks (which in the
    link simulator is most of them) therefore got a discontinuity driven through the middle of it - and the
    measured result depended on the harness's block size, which alone disqualifies the number. The model is
    now streaming: filter, envelope and RNG state persist in the object, multipath keeps the tail of the dry
    signal as history, the SRO resampler carries a continuous read position, noise is added in front of the
    AGC (so the AGC cannot change the in-band SNR), and `reset()` clears the state between sessions. Note
    what this did *not* fix: the residual frame errors, which is why item 20 exists.
19b. **`feed_pcm` rescanned the whole capture window on every callback** (**fixed**). `Modem::rx_capture`
    reports the burst's start position only on success, so while a burst was still arriving the detector
    re-correlated the entire 1.2 s window once per millisecond: a 5.6 s virtual session cost 152 s of wall
    clock. `rx_capture` now reports the position on every path, `feed_pcm` front-trims to it and decodes from
    a fixed offset while the burst arrives, and `run_link_sim`/`ni demo` pump 10 ms blocks (the size a real
    audio callback uses) instead of 1 ms. The same session now runs in under a second. A/B check: forcing the
    old rescan changes no measurement outcome, so this was pure harness cost, not a hidden effect.
20. **A ~26 dB receiver floor that no acoustic SNR removes** (found by comparing `ni bench` with
    `ni linksim` on the same profile, **not fixed**). Single-shot bursts decode perfectly (frame success
    1.000 at 3.0 % raw BER, FEC cleans it to 0) while the *same* modem in the streaming model loses about one
    frame in ten to a bad CRC - and `measured_snr_db` refuses to rise above ~26 dB however loud the signal
    is asked to be, which is the signature of a distortion floor rather than noise. The remaining candidate
    is timing acquisition: in the streaming model a burst starts at an arbitrary offset in a noisy window, so
    the few samples of refinement error rotate each subcarrier relative to its neighbours (a per-bin phase
    ramp the pilot-based estimator only partly removes). The work item is a per-symbol timing/phase tracker
    (common-phase-error correction plus CP-based fine alignment), not another SNR sweep.
21. **`ni demo` cannot pair** (**fixed**; the root cause turned out to be neither the modem nor the
    proxy - see defect 32, whose cross-wired audio pump made this impossible by construction, and defect
    33, which had adaptation switching one endpoint and not the other). The original note, kept because it
    is what the symptom looked like from the outside: `giver=wait-response receiver=wait-challenge`, with
    the giver transmitting and the receiver never hearing it. Gate E below is now PARTIAL rather than FAIL:
    the HTTP leg is verified end-to-end in the model, the CONNECT leg still is not.
22. **A permanently lost frame silently wedges the whole message** (**not fixed**). When a frame exhausts
    `max_retries` (5) the ARQ drops it from the retransmit queue and the peer's reassembler never completes,
    but nothing tells the message layer: `Node` keeps reporting the stream as in progress and an application
    waiting on a multi-kB transfer waits forever. The fix is a per-message abort with an error, plus raising
    or removing the retry budget for a bulk transfer; both are MAC-layer work.
23. **`evec_pct` from `ni bench` is not a usable metric** (**not fixed**). It reports 66-87 % EVM on runs
    that decode 100 % of frames correctly, which is self-contradictory; `ni phy test` on a similar channel
    reports 11.2 % for the same profile. One of the two measurement paths is wrong (most likely the bench
    path, which computes error against unconstrained reference symbols including pilots and unused bins).
    Until that is resolved, quote raw/fec BER and frame success from the sweep, and do not use the EVM
    column from `bench_sweep.csv` as evidence of anything.
24. **`t_arq` passed on Linux and failed under MSVC** (**fixed**; it was defect 25, not a Windows quirk).
    The Windows CI job runs the same eight suites against the same sources and reported
    `1 tests failed out of 8`, only the `memcmp` at `t_arq.cpp:251` - while the byte-count check on the
    line above it passed. "Right length, wrong bytes, only on one allocator" is not an ABI difference, so
    the transcript step in that job was extended to quote ctest's `--output-on-failure` block, which
    located the failing check in the out-of-order replay path of the test's reverse-fed PDU case.
25. **Use-after-free in `ArqEngine::on_pdu`'s out-of-order replay** (**fixed**, found through 24). The
    delivered-run loop declared the buffer holding the re-decoded frame *inside* the loop body, so the
    vector died at the end of an iteration while the next iteration was still handing its data pointer to
    `deliver_data()` (which re-reads the header, hence `ni_rd16` in the ASan trace). glibc's freed blocks
    kept their contents, so on Linux the test passed and the code worked by luck; MSVC's heap did not
    reproduce that, so the same C++ was wrong on both platforms and only one of them told us. Fix: the
    buffer is declared in the loop's enclosing scope (`hold`), with the reasoning in the comment.
    Evidence, both runs on this machine with `-fsanitize=address -g -O1`:
    before, `heap-use-after-free ... READ of size 1 ... SUMMARY: AddressSanitizer: heap-use-after-free
    common.cpp:137 in ni::ni_rd16`; after, `52 checks, 0 failures` and no ASan report.
    Confirmed from the other side on the next CI run: `100% tests passed out of 8` on MSVC.
    The consequence for the product is bigger than for the test: out-of-order arrival is the normal case
    on a half-duplex acoustic link with retransmits, and every message that took that path was reading
    freed memory. Re-measured after the fix (medians of 3 trials, `--max-ms 900000`, rows `fix25-*` in
    `reports/linksim.csv`): 38 B each way on FD-LOW 14.8 s (20.5 bps, range 12.0-19.4 s, 3/3 ok);
    228 B 44.15 s (41.3 bps, was 51.16 s / 35.7 bps, 3/3 ok); **2 048 B on FD-HIGH 30.34 s = 540.0 bps
    (3/3 ok)** and on DBPSK-MID 29.96 s = 546.9 bps (3/3 ok) - the two headline numbers did not move,
    which is what a correct-by-luck path looks like when it is made correct.
26. **"Pairing does not complete when bursts are dropped" was a modelling artefact** (**closed - the
    defect was in the model, see 42**). The original entry, kept because it is what the evidence looked
    like at the time: `ni linksim --bytes 38 --profile 10 --snr 25 --no-multipath --burst-loss 5` failed
    in all 3 trials with `pairing did not complete`, side A stuck in `HARDWARE`/`wait-response` after
    1 150 transmitted bursts and zero received. The suspicion recorded here was "the loss model, not the
    handshake logic". That was right, and the model was the whole story: `--burst-loss` flipped its coin
    per 5 ms block instead of per burst, so a nominal 5% damaged 1 - 0.95^40 = 87% of a 200 ms burst. With
    the model corrected to drop whole bursts, the same command pairs and delivers at 5% (12.02 s, 42
    retransmits) and at 10% (13.93 s), and only 30% breaks it - and even there the two ends *pair* and
    the payload stalls in one direction (A 42 of 70 bytes in 60 s) rather than the handshake failing. No
    claim is made about loss tolerance beyond that: a real room's losses are not independent, and this is
    still a model.
27. **The receiver's proxy token is not obtainable from the Android app** (**documented, not fixed**).
    `ReceiverGateway` authenticates local clients with `Proxy-Authorization: Noise <token>`; if no token is
    configured it generates one and only prints its first four characters (`127.0.0.1:8471 token=ab12****`),
    which is the right security posture and makes the proxy undrivable from outside the app, because a
    client cannot present a secret it cannot read. The in-app `Internet test` and `ni link-test` work because
    they use the gateway in-process. The Windows front end now has `--proxy-token <t>` so the same path can
    be exercised with curl on a PC; the app needs a UI field, and a UI change nobody with a device has
    verified is worse than a documented gap. Note that browsers cannot use this proxy at all regardless: the
    scheme is a bearer token, not Basic auth, so `--proxy-user` will not do it.
28. **`/MT` did not apply, because CMake had moved the decision** (**fixed**). Adding
    `string(REPLACE "/MD" "/MT" ...)` to `windows/CMakeLists.txt` looks like a static-runtime build and is
    not one: under policy `CMP0091=NEW` (default since CMake 3.15) the runtime is selected by
    `CMAKE_MSVC_RUNTIME_LIBRARY`, and the flag variables no longer contain `/MD`, so the replace matched
    nothing and MSVC happily linked `MultiThreadedDLL`. The published bundle therefore shipped an exe that
    imported `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll` and `MSVCP140.dll` on a machine where nothing installs
    them. This was caught not by reading the CMake file but by the packaging step, which runs
    `dumpbin /dependents` on the linked exe and records the verdict in `BUILD-INFO.txt`:
    first run `crt: DYNAMIC (/MD) ...`, after setting `CMAKE_MSVC_RUNTIME_LIBRARY` as well,
    `crt: STATIC (/MT): the exe imports no CRT DLL`, with the import list down to
    `KERNEL32.dll ole32.dll WS2_32.dll` and the file grown from 321 536 B to 630 272 B (the CRT is now
    inside it). Both mechanisms are kept in the file, since older CMake or `CMP0091=OLD` needs the flag
    replace. Lesson recorded where it belongs: an artifact's properties are read from the artifact.
29. **The new window shipped a literal where a measurement belongs, and a calling-convention bet**
    (**fixed**). Two of these were found by reading the file rather than by the compiler, which is the only
    reason they are listed: the calibration log line printed the string `"measured"` in the slot where the
    measured payload rate belongs, and the child-window walker inside `--ui-check` was a capture-less lambda
    passed as `WNDENUMPROC`, a conversion that happens to work on x64 and is not something the target's
    calling convention guarantees. Both were fixed in the same commit. The third was caught by CI on the
    first push: `error C2660: 'CreateFontW': function does not take 13 arguments`, the monospace font call
    having lost `DEFAULT_QUALITY`. Recorded here because the interesting part is not the typo: it is that a
    front end is not covered by "the engine passes its tests", and because the fix for the class (a status
    panel may not contain literals; a UI may not bet on a calling convention) is not the fix for the
    instance.
30. **The windowed app crashed on its first run, and nothing can say where** (**fixed, cause narrowed but
    not pinned down**). CI ran the exe rather than only linking it, and `ui-check` exited `-1073741819`
    (`0xC0000005`, access violation) having written no `ui-check.txt` at all - an exe that dies on launch
    passes every build and every unit test this repository has, which is the whole argument for running the
    artifact. Three changes went in together and the next run passed, so this item cannot honestly claim
    which one was the crash: the breadcrumb tracer and exception filter that make the next one diagnosable
    (see defect 31 for how the first attempt at a diagnosis failed), the device enumeration moved out of
    `WM_CREATE` where a COM failure was indistinguishable from "the window could not be created", and an
    uninitialised `PROPVARIANT` in `friendly_name()` that `PropVariantClear()` was reading unconditionally -
    stack garbage whose `vt` decides whether a pointer gets freed, which is a 0xC0000005 waiting for the
    right stack layout. Also removed: `printf` in a windowed process whose CRT stream is never connected,
    and a NULL callback passed to `EnumChildWindows`. All four are gone, and the fix for the class is the
    tracer: the next crash writes the step it reached and the exception address before it dies.
31. **The transcript added to explain failures was itself unreadable, twice** (**fixed**). First, the guard
    that refuses to publish an exe failing its own `--ui-check` contained an unterminated PowerShell string,
    so the packaging step failed to parse and **not one line of it ran** - no `pkg.log`, no bundle, no
    diagnosis, and the commit comment had no packaging transcript because there was nothing to post. The
    workflow now passes a crude whole-file check that every code line has an even number of double quotes,
    which would have caught it. Second, the tracer then printed `window=牣慥整d`, because a narrow literal
    `"created"` was passed to `%ls` in MSVC's *wide* printf family, where `%ls` means `wchar_t*`. Both were
    found by reading the output rather than the code, which is the point: a failure that cannot be read is
    a failure that will be repeated.

32. **`ni demo` could never pair, because each node heard its own echo** (**fixed**). The demo's audio
    pump filled its two buffers from the wrong endpoints and then fed each node the buffer it had just
    produced itself: `r2g` (receiver-to-giver) held the *giver's* playback, which was then handed to the
    giver's own capture, and vice versa. Nothing ever crossed between the two nodes, so the giver waited
    for a response to a challenge no one could hear and the receiver waited for a challenge that never
    arrived - the exact symptom the defect list carried since item 21 ("`ni demo` cannot pair:
    giver=wait-response receiver=wait-challenge"), which was never a modem problem at all. Fixed by
    swapping the two feeds; `ni demo` now pairs (SAS printed identically on both ends) and returns a real
    HTTP response through the acoustic session. Two more things in the same command were wrong for the
    same reason it had never been noticed: the default profile was 5 (QAM16-WIDE), which the self-test
    scores 0/8 - so the one command documented as the end-to-end test was configured to fail before it
    started - and the verdict line printed "DIFFERENT" when the *control* fetch returned nothing, making a
    working transfer look broken. (This item's original text also said the demo now "returns a real HTTP
    response through the acoustic session", on the strength of a 108-byte capture that turned out to be
    our own proxy's 407 error page - defect 36. What this item fixed is pairing; the response leg is
    defect 41 and is still open.) Defaults are profile 10 with the modelled multipath off (the demo's job
    is to show the path working; `--multipath` still asks for the hard room), and the comparison line now
    distinguishes INCONCLUSIVE from DIFFERENT.
33. **Adaptive modulation was on by default and could deafen the link permanently** (**fixed**). Every
    `Node` - the Windows app, the Android app, the CLI - had `adaptive_ = true`, while only the link
    simulator ever called `set_adaptive` (to turn it *off*). When adaptation fired, `request_profile()`
    rebuilt that endpoint's own modem **immediately** and sent a best-effort CTRL frame asking the peer to
    do the same; the peer's handler set the ARQ's idea of the profile and never touched its modem. One
    lost CTRL frame - or simply the peer acting on a stale modulation id - and the two ends were on
    different profiles with no way back: deafness by design. It fires after six bursts with a poor success
    ratio, which is exactly the state of a real link in its first seconds, and it was visible in `ni demo`
    as `"adaptation": "fallback -> QAM16-WIDE"` on the receiver while the giver stayed on FD-HIGH-DBPSK.
    Fixed three ways: adaptation is **off by default** (the simulator's `--adapt` still demonstrates it);
    it cannot fire before the link is up, so a pairing handshake can never be interrupted by it; and a
    change is now committed **only after the peer acknowledges it**, with the request abandoned if the
    acknowledgement does not arrive, so the two ends are always on the same profile or on the old one.
34. **The apps never told the link when their bursts had finished playing** (**fixed; measured to cost
    time, not shown to block pairing**). `Node::step` reported the transmit backlog only when a modelled
    channel existed (`chan_ && pace_tx_`), so in both apps the link believed a burst was over the moment
    the samples left the library - up to a whole sound-card buffer before the sound left the speaker, on
    the very clock the half-duplex turn-taking uses. The link simulator could not show this because it
    *has* a channel, and it never modelled a device queue at all. Both apps now read their own audio
    backend (WASAPI `GetCurrentPadding`, Android `framesWritten - playbackHeadPosition`) and hand the
    count to the engine before every step, the ABI gained `ni_abi_set_tx_backlog` for that, and the
    simulator gained `--device-ms N` / `--no-device-report` to model a queue and to model an endpoint that
    is not told about it. Measured (38 B, profile 10, 3 trials at 1 trial each, 90 s budget): no queue
    12.02 s; 100 ms queue **unreported** 15.90 s; 100 ms queue reported 19.54 s; 300 ms queue unreported
    15.95 s; 300 ms queue reported 21.05 s. All five delivered the payload and verified it, so this is a
    throughput and timing-accuracy defect, not the explanation for a link that never paired - recorded that
    way rather than promoted into a story that fits.
35. **An empty passphrase meant nothing happened, silently** (**fixed, and this is the one that matters
    most for a first run**). `Node::start()` only calls `begin_pairing()` when the passphrase is non-empty;
    with an empty one no challenge is ever sent, no match code ever appears, and **no code path said so**.
    Both front ends shipped with the passphrase field empty, so "press Start on both ends" produced two
    silent endpoints by default. The core now carries a spoken reason (`pairing_note`, in the status JSON
    and on both status panels), the windowed app refuses to start with a dialog that names the problem and
    puts the cursor in the field, the phone app refuses in its results box, the console app refuses at
    startup unless `--allow-unpaired` is passed deliberately, and both apps now default to the *same*
    profile (10) and session id (7) instead of the phone defaulting to profile 2/session 0 while the PC
    defaulted to profile 11/session 7 - two apps whose defaults differ cannot pair by accident, and that
    was another way to arrive at exactly the reported symptom.

36. **The demo measured its own proxy's error page and called it an origin response** (**fixed**).
    `ni demo` never sent the receiver proxy's bearer token, so every proxied request was answered by the
    proxy itself with `407 Proxy Authentication Required` and a 106-byte error page. That byte string is
    what the demo counted, hashed (`8e1ad3ec…`), printed as "108 bytes came through the acoustic link"
    and, in the first version of section 4.7 below, wrote into this file as a real HTTP response from
    `api.github.com/zen`. It was not: no origin was ever contacted on that path, and the receiver's own
    report said so all along (`proxy_receiver: requests_ok 0, bytes_relayed 0`, `proxy_giver:
    fetches_ok 0`). The demo now reads the token from the receiver node, sends it, prints it, and marks
    the whole run INVALID when the proxy answered the request itself, naming the code. Two further
    harness faults were in the same block and are fixed with it: the proxied leg captured the origin's
    response headers while the direct leg captured only the body (so no comparison could ever be equal
    on a perfect link), and the default URL returns a different body per request, so "DIFFERENT" was a
    statement about the URL rather than about the link. The default origin is now started by the demo
    itself, deterministic, web-server-free, and every run classifies the origin with two direct fetches
    before any acoustic traffic: stable, dynamic, or unknown.
37. **The fragments of a message each claimed to be the whole message** (**fixed**). `ArqEngine::
    send_message` split anything larger than one frame into fragments and copied the caller's flags into
    all of them, OR-ing the per-fragment bits on top: a 60-byte request that needed three fragments
    arrived as three messages flagged `FIRST|LAST`. The giver's fetch helper took the first one for a
    complete request, marked its header complete after 14 bytes, and could never parse it, so every
    proxied HTTP request died - and the failure was invisible because the counter it landed in
    (`fetches_fail`) increments in five places. Found by adding an environment-gated trace
    (`NI_GATEWAY_TRACE=1`) that narrates the helper and now stays in the tree. FIRST is set only on the
    first fragment and LAST only on the last, with the caller's two bits stripped first.
38. **A host with an explicit port could never be resolved** (**fixed**). `parse_url` split `host:port`
    with the condition `c > hp.rfind(']')`, and for a host with no brackets `rfind(']')` is `npos`, so
    `c > npos` is false and the port was never split: `getaddrinfo("127.0.0.1:40809")` failed. Any URL
    with an explicit port was unfetchable, and the default-port case hid it. Found from the gateway
    trace, which printed 3348 identical DNS failures for a single request.
39. **A failed fetch was retried 200 times a second, forever** (**fixed**). `GiverGateway::pump` called
    `step()` and threw away the return value, so a stream whose socket never opened stayed in the map
    and was retried on every pump pass. One bad URL produced 3348 DNS attempts, a `fetches_fail` of
    3348 instead of 1, and a client that waited out the full proxy timeout for an answer that was known
    immediately. The stream is now finished on the first failure, and the reason reaches the client.
40. **The request leg of a proxied HTTP fetch never completed** (**fixed; this was the last blocker and
    it is worth reading as one defect with one root cause**). With 36-39 fixed, a proxied request now
    travels the whole path and the origin answers: the receiver's proxy forwards the request, the link
    carries it in 14-byte fragments (the ARQ payload at these profiles), the giver's helper parses the
    head, resolves `127.0.0.1`, connects, and the origin receives
    `GET http://127.0.0.1:PORT/document.txt HTTP/1.1`. What follows is defect 41.
41. **The response leg still does not complete** (**documented, not fixed - this is where the HTTP leg
    stands**). After the origin answers, the helper pushes the response (185 bytes for a 100-byte
    document, in one `push`, then the empty LAST chunk that marks the end) and the receiver's ARQ
    reports the frames as malformed: in the measured runs `rx_malformed` is 23-98 with `rx_payload_bytes
    0` on the receiving side, and the receiver's proxy answers 504 after its timeout. The request
    direction carries the same 14-byte fragments without trouble, so this is specific to the
    giver-to-receiver direction of a back-to-back burst train, not to fragmentation or to the proxy.
    Not diagnosed yet, not claimed to work anywhere.

42. **`--burst-loss` did not mean what it said, and a pairing failure was diagnosed against it**
    (**fixed**). The flag is documented as "fraction of bursts the model drops entirely (fades /
    interruptions)" and the implementation flipped its coin per *pulled block* - 5 ms of audio - so a
    200 ms burst containing about forty blocks was damaged with probability 1 - 0.95^40 = 87%. Every
    "loss" measurement in this repository was therefore taken against a model that was far harsher than
    its name, and defect 26's `pairing did not complete` conclusion came from it. The coin is now flipped
    once, when playback goes idle-to-busy (a burst boundary), and the burst is dropped whole. Re-measured
    afterwards: 38 B, profile 10, no multipath - 0% 12.02 s (identical to before, as it must be), 5%
    12.02 s **ok** (was FAIL 3/3), 10% 13.93 s ok, 30% pairs but the payload stalls in one direction
    (A 42/70 bytes in 60 s). The known limits of what that shows are in the RESULTS entry for defect 26.
43. **The two apps shipped defaults that could not pair with each other, and the core's own defaults
    were a third answer** (**fixed**). The phone's service fell back to profile 2 / session 0 when its
    intent extras were absent - which is exactly what happens when the platform restarts the service -
    while the PC opened on profile 10 / session 7, and the library's `NodeConfig` defaulted to profile 2
    / session 0. Two endpoints on different profiles or different session ids transmit in a language the
    other is not listening to, permanently and silently. All three now agree on FD-LOW-DBPSK (10) and
    session 7, and both apps display the profile and session they are running so a mismatch is visible.
44. **The engine would start with no passphrase and then do nothing at all** (**fixed at the source, not
    only in the UIs**). `Node::start()` sent no pairing challenge when the passphrase was empty and
    reported no error: the peer stayed offline for ever and nothing on either screen said why. Both apps
    already refuse to start in that case, but the guarantee belonged in the engine, so `Node::start()`
    now returns `NI_ERR_PARAM` and fills `pairing_note` with the same sentence the panels render. The ABI
    test asserts it through the status JSON, because a refusal the UI cannot show is a refusal the user
    cannot act on (t_abi: 33 -> 39 checks). `ni calibrate` sets `allow_unpaired` explicitly, since it is a
    solo measurement with no peer to pair with.
45. **The phone's profile list was unreadable, and there was no way to notice it had been guessed
    around** (**fixed**). `MainActivity` handed the string from `ni_abi_profiles_json()` to
    `JSONObject(...)`, which expects an object; the library returns a JSON *array*, so `org.json` threw
    `Value [{"id":... of type JSONArray cannot be converted to JSONObject` and the profile selector held
    the single entry `#-1 profile table unavailable`. The parser now accepts a top-level array or an
    object with `profiles`/`items`, drops entries whose id is negative, and - the part that matters - the
    start button refuses to run while the selection is `-1` instead of sending a guessed profile number
    to a peer that is waiting on a different one. The first field report could not tell the two apart,
    because a guessed profile and a mismatched profile look identical from the outside.
46. **Six panel fields read JSON keys the core does not write** (**fixed**). The status JSON's names are
    the ones `StatusSnapshot::to_json()` writes; the Kotlin status parser had been written against
    paraphrases - `profile_name` (core: `profile`), `useful_bps_up` / `useful_bps_down` (core:
    `useful_up_bps` / `useful_down_bps`), `retries` (core: `retransmits`) - so the profile, both useful
    rates and the retransmit count were blank on every screen of every build, and nothing failed loudly
    because every one of them was optional. All four now use the core's spelling with the old ones still
    accepted as fallbacks, and an audit of every remaining field found no other mismatch. The core's key
    list is now the single reference the panel is checked against. The Windows GUI was checked in the
    same pass and is clean: it links the struct, not the JSON, so the misnames could only ever bite on
    the Android side.
47. **WASAPI capture dropped every sample that did not fit in the caller's buffer** (**fixed**).
    `WasapiEngine::capture` read exactly one device packet per call, copied `min(packet, frames)` of it,
    and then called `ReleaseBuffer(packet)` for the whole packet. Whatever did not fit was gone - no
    error, no counter - and it is dropped *inside* the burst the peer is transmitting, because the
    capture pump is called at the modem's block rate, not the device's packet rate. On a device that
    hands over packets larger than the block, the tail of every packet is lost; the audio that reaches
    the demodulator is a packet-length comb, which is exactly the kind of thing that shows up as
    `rx_malformed` on the far end rather than as an obvious failure here. Capture now keeps a hold-over
    buffer: a drained cursor for what was left over, then it keeps pulling packets while the caller's
    buffer has room, and the remainder is handed over at the start of the next call. `ReleaseBuffer()` is
    still called with the packet's own length - releasing a shorter count is not a thing WASAPI allows -
    so the fix had to be in the copy, not the release. (Not to be confused with defect 41: this is a
    Windows-side sample-loss bug, found by reading the code, and it has not been exercised against a
    sound card.)

## 2. Coding gain and the cliff (measured, `t_fec`, current code)

Rate-1/2, K=7, g1 = 0o133, g2 = 0o171, hard-decision Viterbi, 1 136 information bits per block:

Extending the budget to 30 s of transfer time for one trial each on profiles 2, 3 and 11 changed
nothing: `delivered 0`, `retransmits 8–37`, `lost_frames 0–5`, `A got 0 B got 0 of 228 bytes`.

What *is* demonstrated by these runs, and was not before this session:

* **Pairing completes over the modelled acoustic link.** `diagnostics_json()` reports
  `"pairing":"paired"` on both endpoints, and `"pairing":"wait-confirm"`/`"failed"` exactly when the
  state machine says so. `"pairing":"wait-response"`/`"wait-challenge"` with 0 rx bursts is the
  signature of the QAM16 rows, i.e. one side cannot read the other at all.
* **Frames flow in both directions and the ARQ loop is live:** `rx_frames` 20–72 per side,
  `acks_sent` 1–52, `rtt_ms` 231.5 (paced, profile 11) and 1099–1209 (unpaced, profile 3),
  `retransmits` up to 37 with `lost_frames` 0–5.
* **Pacing matters, and unpaced simulation is not a substitute.** The same profile 2 configuration
  completes pairing when paced and fails it when unpaced, because the master speaks over the slave's
  reply window. Any figure produced by the unpaced mode would have been an artefact.

What is **not** demonstrated: an end-to-end byte-for-byte payload exchange between the two nodes.
The DATA path is verified end to end at the unit level (`t_arq` 52 checks: fragmentation, three-burst
transfer with `lost_frames 0`, retransmission after a swallowed burst, out-of-order reassembly, AEAD
round trip, tamper and replay refusal) and single frames are verified at the PHY level
(`ni render` → `ni decode` → matching SHA-256 of the decoded payload). Between those two layers the
link does not currently complete a transfer in the simulated time, so **this repository reports no
throughput number, no "internet sharing" claim, and no transfer-time claim.** The remaining suspects,
in order of likelihood:

1. Achievable demod SNR through the device model is far below the nominal `--snr`: measured
   `band_snr_db` is −14 to −45 dB on runs configured at 35 dB, so most bursts fail and the retry
   budget (5 × `ack_timeout_ms`) expires; `lost_frames > 0` on three of four rows is the same story.
2. The half-duplex window (`turnaround_ms` 40, `listen_ms` 1200, one burst per airtime) has not been
   tuned against the paced model, so a retransmission and the peer's reply can still collide.
3. Rate adaptation is disabled in the simulator (`LinkSimOptions::adapt` defaults to false) because
   the burst descriptor's modulation id is decoded but **not used** to reconfigure the demodulator
   (`modem.cpp`: `(void)hdr_mod;`), so the two ends cannot converge on a profile after one of them
   adapts alone. Making the preamble profile-independent (as 802.11 does with its non-HT preamble) is
   the real fix and is not implemented.

### 4.6 ROOT CAUSE FOUND (this supersedes the speculation above; the suspects listed there were downstream symptoms)

Instrumenting the transmit path of `ni linksim` on the profile that decodes 100 % of single bursts in
`ni bench` produced the answer, and it is not a modem problem:

```
[render_fail] n=346 rc=-13 (NI_ERR_OVERFLOW) max_payload=82 cap=1024
[render_fail] n=370 rc=-13 (NI_ERR_OVERFLOW) max_payload=82 cap=1024
```

`ArqConfig::max_burst_bytes` is 1024, but a burst on FD-LOW-DBPSK carries at most 82 bytes of PDU
(the `maxPay` column of `ni profiles`). So `pack_frames` filled a burst with six 62-byte DATA frames
(372 bytes), `Modem::tx_render` correctly refused it with `NI_ERR_OVERFLOW`, and
`AcousticLink::render_burst` **returned in silence**. The caller still counted the burst as transmitted
and the ARQ still marked those frames in flight, so: no waveform, no delivery, no ack, an eternal
retransmit loop, and counters that looked healthy. Small frames (ACK 44 B, PAIR 58 B) fit inside 82
bytes, which is exactly why pairing succeeded and acks flowed while payload bytes never moved - and why
`ni bench`, `ni phy test` and the WAV round trip, all of which render one frame per burst, worked all
along. Measured with the failure counted: `tx_render_fail` 57 233 bursts on side A and 57 628 on side B
in a 57 s session, during which `tx_payload_bytes` reported 14 MB "sent" that never existed. An `up_bps`
of 5.26 b/s printed in one of those runs was a harness artefact from a stale byte count, **not** a link
rate, and is reported here so it cannot be quoted as one.

Fixes now in the tree, each with the reasoning in the source comment:

1. `render_burst` returns the modem's error; `transmit` does not record a burst that was never
   rendered; the failure increments a new `tx_render_fail` counter that appears in the diagnostics JSON.
2. `ArqEngine::cancel_burst()` releases the frames of a burst that failed to render, so they are
   retried at once instead of waiting for an ack that can never come.
3. The per-burst byte budget is clamped to the modem's capacity **at the `build_pdu` call site**
   (`AcousticLink::tick`). Clamping `ArqConfig::max_burst_bytes` in the link constructor was tried first
   and is not enough: the node assigns its own `ArqConfig` afterwards, which restored 1024. Both are
   kept, and the `measured_airtime_ms 2 686` / `-45 dB` "suspects" above are consequences of this bug,
   not causes.
4. An acknowledgement that does not fit in the remaining burst space is deferred; it no longer abandons
   the data frames already encoded in that burst (returning 0 from `pack_frames` used to discard them
   after they had been marked in flight).
5. `int render_burst` was left without a `return` at the end while the void version was being converted:
   falling off the end of a non-void function segfaulted the `-O1` build and ran "fine" under `-O0`+ASan.
   Recorded because it is a good example of an optimisation-dependent crash being mistaken for a protocol
   bug.

State after the fix, measured on this tree (raw records in `reports/raw/linksim.jsonl`, rows tagged
`fix-*`; every one of them is a SIMULATED CHANNEL measurement, and none is an internet speed):

* the burst overflow is gone - `tx_render_fail 0` on both sides in every run;
* **a session transfer completes.** `ni linksim --bytes 38 --profile 10 --snr 25 --no-multipath` reports
  `ok=true delivered=1` after 12.02 s of half-duplex airtime, and the harness only says `ok=true` when both
  endpoints reassembled the whole message *and* its SHA-256 matched, so 38 bytes each way arrived intact.
  228 bytes each way on the same 82-byte-burst profile completes in 51.16 s (35.7 bps).
* **multi-kB completes on the wide profiles**, which is what gate C asks for: 2048 bytes each way on
  FD-HIGH-DBPSK in 30.34 s = **540.0 bps (67.5 B/s of verified payload)**, and on DBPSK-MID in 29.96 s =
  546.9 bps (68.4 B/s), 2 retries-to-loss ratio aside (83 and 63 retransmits, 2 and 0 frames lost). These
  are the first session-level throughputs this project has measured; the PHY-level numbers in sections 3
  and 4.3 are not comparable to them.
* the harness is no longer the bottleneck: items 19 and 19b (streaming channel model, bounded receive scan,
  10 ms pump blocks) took a 5.6 s virtual session from 152 s of wall clock to under a second, and let the
  45 s transfers be attempted at all.

What still fails, and by how much:

* 2 kB on the narrow FD-LOW profile does not finish: 183 retransmits, 24 frames lost, `A got 294 of 2080
  bytes` after 57.6 s - the ~10 % per-frame error rate of item 20 exhausts the retry budget (item 22).
* multipath still kills the session, and on FD-LOW it kills it before data: pairing never completes
  (`pairing did not complete within 20000 ms`; the responder counted 426 bursts, 363 CRC failures). On
  FD-HIGH the session pairs under the default reflections but 2 kB does not complete (670 of 2080 bytes).
* `ni demo` - the proxy and HTTP leg - does not pair at all (item 21), so gate E remains FAIL.

Gate C is therefore **PARTIAL**: a reliable session (FEC + ARQ + ACK + pairing + AEAD) demonstrably carries a
2 kB message across the modelled link in both directions with hash verification, on 2 of the profiles tested,
in a static channel at 20-26 dB measured SNR; it does not carry that message on the narrow profile, it does
not survive multipath, and it has never been attempted over real speakers and microphones.

### 4.6a Earlier speculation, kept for the record: the same profile that fails in linksim decodes 100 % burst-by-burst

`ni bench --profile 2,3,5,10,11 --trials 3` (315 rows, `reports/bench_sweep.csv` / `.json`) feeds
`ni_phy_test` one padded burst at a time through the same channel model. Medians over 9 trials per point:

| profile | `--snr` target | measured SNR (median) | frame success |
|---|---|---|---|
| FD-LOW-DBPSK (10) | 30 / 22 / 16 / 12 / 8 dB | 26.2 / 25.5 / 23.8 / 21.5 / 18.9 | **1.00 / 1.00 / 1.00 / 1.00 / 1.00** |
| FD-LOW-DBPSK (10) | 4 / 0 dB | 15.5 / 12.1 | 0.67 / 0.00 |
| DBPSK-MID (2) | 30 / 22 dB | 20.2 / 19.6 | 0.33 / 0.33 |
| DBPSK-WIDE (3) | 30 / 22 dB | 20.4 / 19.3 | 0.00 / 0.00 |
| QAM16-WIDE (5) | 30 dB | 16.2 | 0.00 |

Two things follow. First, the model does not honour the requested SNR at all: 30 dB of configured SNR
becomes 20-26 dB measured, and 0 dB becomes 12 dB - the noise is added relative to a level the AGC has
already normalised, so the sweep compresses into a band roughly 4-26 dB whatever `--snr` says. A
"run at `--snr 35`" is therefore not a clean-channel run, and any conclusion drawn from nominal SNR is
wrong; the measured column is the only one to quote. Second, the linksim failure is not a property of the
modem: on the profile where the modem path is essentially error-free one burst at a time, a two-node
session still delivers nothing.

The mechanism now looks like this, and it is visible in `Node::pull_playback`: pending transmit chunks
are accumulated into `raw_tx_` and the channel is applied to **the whole accumulated block at once**
(`chan_->process(&raw_tx_[0], raw_tx_.size(), &processed)`), guarded only by `!link_->tx_ready()`. When
an endpoint has several bursts queued - which is exactly what half-duplex retransmission produces - they
are glued together with no inter-burst guard and processed as one long sound, while `ni phy test` and the
WAV path hand the demodulator one padded burst at a time. The peer diagnostics agree with that reading:
in the FD-LOW run (`reports/linksim.csv`, last row), A's estimator reported **+23.7369 dB** (it was hearing B cleanly) while B's sat on the
−45 dB failure floor, `rtt_ms 0` (no ack ever applied), `retransmits 18`, `lost_frames 0`, `peer_online: false` on both sides, and an earlier
DBPSK-WIDE run measured `measured_airtime_ms 1733` for a profile whose burst is 233 ms - a "burst" that was
really about seven of them glued together. The saved record is `fdlow25-paced` in `reports/raw/linksim.jsonl`, where B's `measured_airtime_ms` is 2 686.67 ms for a 393 ms burst. A `+23.7369 dB` against B's −45 dB is the asymmetry to explain.

A third theory was **tested and made things worse**, which is still information: inserting 1 024 samples
of silence between pending chunks in `Node::pull_playback` (a guard interval, like the WAV tools'
`--pad`) stopped pairing from completing at all on the profile where it previously succeeded. The
likely mechanism is that the guard inflates `measured_airtime_ms`, and the half-duplex reply window is
`4 x airtime_est` - so the window moves out of step with the peer. The change was reverted rather than
left in the tree; a real fix has to bound bursts at the link layer (where the burst length is known) and
re-measure airtime from the modem's own plan, not from received samples.

Two theories were tested and are **wrong**, recorded so nobody re-tests them: the simulator has no
self-interference (A's playback goes only to B's capture and vice versa, `sim.cpp` wire loop), and the
engine does not gate capture while transmitting (`Node::feed_capture` forwards unconditionally).

## 4.7 `ni demo` end to end - what is measured, and what the first version of this section got wrong

`ni demo` is the one command that exercises the whole path: modem, ARQ, pairing, the receiver's local
proxy, the giver's real HTTP client. Its default origin is now a plain-HTTP server the command starts
on its own host, serving a deterministic document of `--document-bytes` bytes (the transcript below is
100 bytes), because every public origin reachable from the test host answers `301` to `https`, and the
`https` route needs the CONNECT tunnel whose TLS handshake has not been made to work over this link
(one attempt: tunnel established, `curl` exit 56, documented in the CONNECT subsection below).

**What works, in every run measured:** pairing completes in ~2.4 s with the same four-word SAS on both
ends; both control fetches succeed and are byte-identical (origin classified *stable*); the receiver's
proxy accepts `curl`, sends the bearer token check, and forwards the request; the acoustic link carries
the request in 14-byte fragments (the ARQ payload at these profiles); the giver's fetch helper parses
the head, resolves the host, connects to the origin, and the origin logs the request:

```
  [origin] GET http://127.0.0.1:45681/document.txt HTTP/1.1
  [gateway] stream 1 GET 127.0.0.1:45681  (host=127.0.0.1)
  [gateway] push id=1 n=185
  [gateway] push id=1 n=0            <- end of response, the fetch completed
```

**What does not work yet:** the response never reaches `curl`. The helper pushes the reply onto the
link and the receiving side reports the frames as malformed (`rx_malformed` 23-98 with
`rx_payload_bytes 0`), after which the receiver's proxy answers `504` when its timeout expires. So the
honest one-line verdict for the HTTP leg is: **request out, origin reached, response not back yet**
(defect 41). No byte of an origin response has ever crossed this link, and the transcript that this
section carried before - "108 bytes came through the acoustic link, sha256 8e1ad3ec…" - was our own
proxy's `407` error page, measured because the demo never sent the proxy token. It was wrong and it is
recorded as defect 36 rather than quietly deleted, because it is exactly the mistake this project's
own rules exist to prevent: a self-generated byte string written up as a real origin response.

The link statistics from the same runs (giver): `mtu 42` (ARQ payload), 14-byte stream fragments,
`rx_duplicates` in the tens while the reply is retried. Nothing here is an internet speed and no
throughput claim is made from it.

### 4.7.1 The CONNECT leg, as far as it has been taken

With `--url https://api.github.com/octocat?s=noiseinternet` (a deterministic 821-byte document, chosen
because the same URL returns identical bytes across fetches, unlike `/zen`) and a 1200 s budget the
run showed: `proxy_giver: connect_ok 1, connect_fail 0` - the helper opened the TCP connection to the
origin on port 443, sent `HTTP/1.1 200 Connection Established` back to `curl`, and began relaying - and
then `curl` exited 56 after 175 s with `HTTP 000` and 46 bytes. So the tunnel *opens* and the TLS
handshake does not complete over this link. That is the state of the CONNECT leg: attempted, not
working, not claimed. A plain-HTTP origin with no explicit port is the only fetch this build has been
shown to start successfully.

## 4.8 What the corrected loss model changed, and what the device queue does not do

Three measurements were re-taken after defect 42 (the loss model dropped 5 ms blocks, not bursts) and
after the device-queue plumbing was added. All of them are single trials unless stated; they are here
because each one closes a hypothesis about the first field report rather than because they are precise.

| experiment | command | result |
| --- | --- | --- |
| burst loss, corrected model | `ni linksim --bytes 38 --profile 10 --snr 25 --no-multipath --burst-loss P` | P=0: ok 12.02 s. P=5%: **ok 12.02 s** (the same command used to FAIL 3/3 - see defect 26). P=10%: ok 13.93 s. P=30%: both ends pair, the payload stalls in one direction (A 42 of 70 bytes in 60 s). |
| a sound-card queue, reported or not | same, `--device-ms 100|300` with and without `--no-device-report` | all four pair and deliver: 100 ms reported 19.54 s, 100 ms unreported 15.90 s, 300 ms unreported 15.95 s, none 12.02 s. **A device queue does not stop pairing**; not telling the link about it costs time, not success, in this model. |
| sample-rate offset between the two devices | same, `--sro 20|100|300` (ppm) | all deliver, ~0.79 s at profile 11 for 38 B: the carrier/SRO tracker copes with 300 ppm, so clock mismatch is not a candidate explanation for a link that never pairs. |

What that leaves, honestly: the model says pairing survives lost bursts (to about 10%), survives a
300 ms device queue, and survives a 300 ppm clock offset. Whatever stopped the first hardware attempt
is therefore *not* one of those three, which is why the front ends now report the things a model cannot
know - the measured input level, whether bursts are arriving at all, and whether they decode - and why
the passphrase/profile/session preconditions are now enforced instead of assumed.

## 5. Reference vectors

`python/gen_vectors.py` (needs `/home/user/env/bin/python`, `cryptography` 50.0.2 installed there)
writes `protocol/protocol_vectors/*.json` and the flat `vectors.txt` (49 vectors) that `t_crypto`
cross-checks. The generator's values were compared against the published numbers before being used:

* SHA-256 `""` → `e3b0c442…`, `"abc"` → `ba7816bf…` (FIPS 180-4 examples, plus the 56-byte and
  10⁶×'a' cases).
* HMAC-SHA256 RFC 4231 case 1 → `b0344c61d8db3853…`, case 2 → `5bdcc146bf60754e…`.
* HKDF-SHA256 RFC 5869 A.1 OKM → `3cb25f25faacd57a…`.
* ChaCha20-Poly1305 RFC 8439 §2.8.2 ciphertext prefix `d31a8d34648e60db…`, tag `65aba0d7…` (13 AEAD
  cases in `vectors.txt`, each checked against `cryptography`'s independent implementation).
* CRC-16/CCITT-FALSE `"123456789"` → `0x29b1`, CRC-32 → `0xcbf43926`, FNV-1a → `0xbbcf…`; the frame
  header CRC-8 is poly 0x07 with **init 0xFF**, so the usual `0xF4` check value does not apply and the
  frame test asserts the implementation's own value (`0xc0` for the reference header).

## 6. What the code base contains

`shared/acoustic_core/` — 20 C++ sources, 18 headers, one static library used unchanged by the CLI,
the Android JNI shell and the Windows build: versioned frame codec (16-byte header, CRC-8 header
check, CRC-32 payload check), OFDM modem (N_FFT 256, 16 modulation profiles, 24-bit burst descriptor
carrying length and modulation id, band-limited PN-BPSK sync pair, pilot-based channel estimation,
rate-1/2 K=7 Viterbi with erasure marking, block interleaver, self-synchronising scrambler, soft LLRs),
ARQ with cumulative + bitmap selective acks, replay window, ChaCha20-Poly1305 AEAD on DATA and a
truncated MAC on control frames, HKDF-SHA256 session keys with a 4-word SAS code, challenge-response
pairing with attempt limits and backoff, half-duplex turn-taking with an FDD + NLMS-AEC experiment, a
local CONNECT/HTTP proxy with per-stream reassembly and size caps, a link simulator driven by the same
`Node` class the apps use, and a flat C ABI (`ni_abi_*`) for the platform shells. `scripts/` holds the
build, syntax-check and CSV-conversion entry points. `android/` and `windows/` are the platform shells
(source only, never compiled - see `docs/STATUS.md` section 10), `tests/physical/` is the over-the-air
protocol with a runner that refuses to write a row when the hardware is missing, and `artifacts/` is empty
on purpose. `docs/ADR-001` records the architecture decisions, `docs/STATUS.md` the per-milestone state,
`protocol/modulation_profiles.json` the PHY table.

## 7. NOT TESTED on this host (and therefore not claimed)

* **Sound in air.** No speaker, no microphone, no acoustic tube, no room. Every PHY number above is
  the modelled device chain in software. `ni audit` reports `audio devices: 0`, `over-the-air
  testing: NOT TESTED`.
* **Android app on a device.** `android/` holds Kotlin (UI, `AudioRecord`/`AudioTrack` engine, foreground
  service, UDP/DNS `VpnService` tunnel), a JNI bridge to `ni_abi_*`, Gradle and NDK CMake files. It is
  compiled by CI (AGP 8.5.2, Kotlin 1.9.24, NDK r26 - see section 6, which is where the truth about the
  artifacts lives), and it has **never been installed or run**, because no phone and no Android toolchain
  exist in the environment where this text was written. The debug keystore is created on the CI runner and
  destroyed with it, so the APK's signature is installable, throwaway and not a release signature.
* **Windows app against real hardware.** `windows/` holds a WASAPI backend (device enumeration, shared-mode
  render/capture), a windowed front end and a console front end with CMake. CI compiles all of it with MSVC
  19.51 and runs the window itself (`--ui-check`, whose transcript ships as `ui-check.txt`) - see section 6.
  What is still untested is the part no build agent can test: sound. No MSVC build host in this project has
  ever had a speaker or a microphone, so the audio path's compile-time correctness is proven and its
  acoustic behaviour is not. `bash scripts/syntax_check.sh` checks that the shared core parses with the host
  compiler; it does not compile the Windows-specific files.
* **Real device audio enumeration** — `ni_abi_audio_enumerate` returns `NI_ERR_UNSUPPORTED` in this
  build (the WASAPI enumerator is compiled only into the Windows target).
* **Echo cancellation on hardware** — `NlmsAec` is unit-exercised in the `ni duplex` command against
  the modelled channel only.
* **Internet sharing.** No proxy session was ever carried over an acoustic link, no external host was
  contacted from the sandbox, and the local HTTP proxy path (`ni proxy`, `ni link-test`) has only been
  exercised over the simulated link. Any statement of the form "the phone shared its internet with the
  PC" would be unsupported by anything in this file.
* Link speed versus useful throughput: not measured, because no transfer completed.

## 6. Gate G, the platform artifacts, as measured

The Android and Windows halves of this project existed only as source until CI compiled them, so the
first honest statement about them is the compiler's, not mine. The sizes below are from the *first* green
publish (run `38430714969`, commit `8deef18`); every green push since then rebuilds both files and
republishes them under the same tag with its own digests in the release body, which is why
`artifacts/README.md` carries the newer numbers and this section is a dated record.

* `gradle :app:assembleDebug` (AGP 8.5.2, Kotlin 1.9.24, JDK 17, NDK r26): **succeeded**, producing a
  4 093 450-byte debug APK whose contents were checked in the same job -
  `lib/arm64-v8a/libnoiseinternet_jni.so` 284 312 B, `lib/x86_64/libnoiseinternet_jni.so` 317 144 B,
  `classes.dex` 2 313 184 B - because an APK without the native core inside it would be a hollow
  success and this job refuses to call that a pass.

  and all eight test executables; `ctest` on that platform reports 8/8 - and the only reason it ever
  reported 7/8 is defect 25: the Windows compiler was right and the code was wrong on every platform.
* **The Windows exe is standalone, and that was measured rather than declared** (defect 28 is why the
  distinction matters). `NI_STATIC_RUNTIME=ON` asks for `/MT`; the packaging step then runs
  `dumpbin /dependents` on the file that got linked and writes the verdict into `BUILD-INFO.txt`. Current

  carry the pairing state and the SAS words (they existed only inside the diagnostics JSON, which is why no
  front end could show the four words a human compares before trusting an encrypted link); CI had to gain a
  way to exercise the window on a machine with no audio - that is `--ui-check`, which creates the window,

  step runs it with a 60-second bound and appends its transcript to the build log; and the first push of it
